# Writing Skills PoC — japanese-tech-writing / cognitive-rhythm-writing

Date: 2026-09-26 (JST)
Status: PoC result and adoption proposal (ADP-031-B, Story ADP-031, Epic ADP-EPIC-06)
Scope: Compare the same Android technical article written under three conditions
— no skill / `japanese-tech-writing` / `japanese-tech-writing` + `cognitive-rhythm-writing` —
and record readability, technical accuracy, and over-conversion so the adoption
conditions for each skill can be decided. Operational state (Status, time
records) stays in the Notion Task; this document is the durable evidence.

## Method

- One brief, one fact sheet ([brief.md](brief.md)): "where to keep screen state:
  `remember` / `rememberSaveable` / `ViewModel`", 1,800–2,500 chars, 3–5 headings,
  2–3 Kotlin examples, facts 1–7 mandatory.
- Each condition was generated by a fresh Claude Sonnet subagent that saw only the
  brief and (for B/C) the skill files, so no condition could see another's output.
- Evaluation had three layers:
  1. Mechanical check ([lint.py](lint.py) → [lint-result.json](lint-result.json)):
     banned-phrase counts from `japanese-tech-writing`, leak test vocabulary from
     `cognitive-rhythm-writing`, sentence length, fact coverage.
  2. A blind review by a separate Claude session acting as a senior Android
     engineer and Japanese technical editor ([blind-review.md](blind-review.md);
     key: **X = C, Y = A, Z = B**).
  3. Manual cross-check of every accuracy finding against the fact sheet and the
     Compose API.
- Limitation: n = 1 per condition, one topic, one model, and the reviewer is also
  an LLM. The findings show *failure modes*, not stable averages.

## Results

| | A: no skill | B: jtw | C: jtw + crw |
|---|---|---|---|
| Readability (blind, 1–5) | 4 | 3 | 4 |
| Technical accuracy (blind, 1–5) | 4 | **2** | 4 |
| Blind verdict | Publish after edits (closest) | Not publishable as-is | Publish after edits |
| jtw banned phrases (mechanical) | 4 | 0 | 0 (1 false positive) |
| Avg sentence length (chars) | 46.5 | 48.3 | 36.8 |
| Sentences ≥ 80 chars | 4 | 1 | 0 |
| Facts 1–10 covered | 10/10 | 10/10 | 10/10 |
| Generation cost (subagent tokens / wall time / self-revision passes) | 67k / 43 s / 0 | 82k / 117 s / 1 | 98k / 201 s / 2 |

Mechanical-check false positives: the `回収` leak hits in A and C are "memory
reclaim" (メモリ回収), and `ここでは` in C is "does not happen here" — neither is
a skill-vocabulary leak or an agenda sentence.

### What each skill changed

**`japanese-tech-writing` (B)** removed every LLM-ish filler phrase that A had
(`この記事では`, `において`, `筋が悪い`, `ここまでの内容を整理すると`) and made
causal mechanisms explicit (e.g. why `ViewModel` survives rotation but not
process death). It also produced the only fatal error of the PoC:

> 入力欄の一文字ごとの値やスクロール位置は前者に、サーバーから取得した一覧…は後者に

In the preceding sentence 前者 = `ViewModel`, so the article tells the reader to
do the opposite of fact 10. The opening also contradicts fact 1 ("コンポーザブル関数の
外に保存場所を持たない限り…初期値へ戻る") and overclaims ("個別に悩む必要はない").
The pattern matches the skill's compression and "言い切る" rules: parallel facts
were merged into one sentence with a pronoun reference, and hedges were removed.
The skill's own rules forbid both outcomes ("短文化は…同一性…が順読みで明示された
まま保てる場合に限る", "必ずできるかのように書かない"), so the problem is that a
single-pass generator does not reliably apply its own checks.

**`cognitive-rhythm-writing` on top (C)** produced the most readable structure
(symptom → failing code → fix → rotation → `rememberSaveable` → `ViewModel`),
the shortest sentences, and no long-sentence runs. Accuracy stayed at A's level.
Its over-conversion is on the rhetoric side:

- The title "画面を回しただけで消える値" hides the topic (`remember` /
  `rememberSaveable` / `ViewModel`), which the brief named.
- The opening tension "原因は一つとは限らない" is never explicitly resolved — the
  skill's own tension-ledger check should have caught it.
- A staged hesitation ("…起きない類の不具合だろう、と思いたくなる") and a preachy
  close ("その期待自体を見直す番である") reduce clarity.
- Content added beyond the fact sheet was slightly wrong: "リストであれば
  `listSaver`、キーと値の組であれば`mapSaver`" misdescribes `listSaver`.

**No skill (A)** was the most complete and closest to publishable, but carried
the filler phrases the skills target and an ambiguity that conflicts with fact 8
("再びアプリを開いたときにも残っていてほしいなら `rememberSaveable`…").

## Adoption proposal

Neither skill replaces a technical accuracy review; B shows that applying a
style norm can *introduce* an accuracy error while improving surface style.

| Skill | Proposal | Invoke when | Do not invoke when |
|---|---|---|---|
| `japanese-tech-writing` | **Adopt conditionally** as a revision/review norm | Revising a finished draft of a Japanese technical document before publication; running the banned-phrase and translationese checks on AI drafts | As the only norm for first-pass generation from a fact sheet without a follow-up accuracy review; English documents; operational notes (journal, Notion Result) where speed matters more than prose |
| `cognitive-rhythm-writing` | **Adopt as opt-in** for read-through articles only | note / AOD articles and essays meant to be read end to end, after the jtw pass | Reference docs, how-to/API guides, README, specs, PR bodies — anything scanned rather than read |

Required gates when either skill is used:

1. **Accuracy review after the style pass**, by a different session or person,
   with explicit checks for pronoun references (前者/後者, これ/それ), removed
   hedges, and any content added beyond the source facts.
2. **Brief conformance check**: title and headings keep the topic keywords;
   length and structure constraints still hold after the rewrite.
3. For `cognitive-rhythm-writing`: run its tension ledger (点検手順 3) as a
   separate step and resolve or remove every opened question.

Cost: the skills added roughly 20–45 % tokens and 3–5× wall time per article in
this run. That is acceptable for published articles, not for routine notes.

The pipeline wiring (which ADP gate calls these skills) belongs to the
follow-on integration work in ADP-EPIC-06 (PoC pass criterion 5); this document
only supplies the evidence and the proposed call / no-call conditions.
