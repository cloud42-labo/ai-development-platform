## X

### 1. 読みやすさ：4/5
「回転で入力が消える」という症状から入り、`remember` の失敗例→修正→回転での消失→`rememberSaveable`→`ViewModel` と、読者が実際につまずく順に沿っていて引き込まれる。ただし物語調に寄せた一文（「冒頭の入力欄の消失は、ここでは起きない類の不具合だろう、と思いたくなる。」）は論理的な位置づけが分かりにくく、流れを一瞬止めている。

### 2. 技術的正確性：4/5
コードはすべてコンパイル可能で、記述どおりに動く（`var count = remember { 0 }` はローカル var のキャプチャで、押しても表示は変わらない。`rememberSaveable(stateSaver = ...)` の MutableState オーバーロードも正しい）。問題になりうる箇所は次のとおり。

- 「リストであれば`listSaver`、キーと値の組であれば`mapSaver`と、保存したい形に合わせて選べる。」：誤解を招く。`listSaver` は保存対象がリストであるときの専用品ではなく、任意のオブジェクトを値のリストへ直列化する Saver。`mapSaver` との違いはキー名で取り出すか位置で取り出すかにすぎない。「リストを保存したいなら listSaver」と読まれると選び方を間違える。
- 「任意のデータクラスはそのままでは弾かれる。」：「弾かれる」がコンパイルエラーなのか実行時例外なのか曖昧（実際は保存時の実行時例外）。
- 「`ViewModel`が持つ`SavedStateHandle`」：`ViewModel` が標準で持っているわけではなく、コンストラクタで受け取る必要がある。初学者は「プロパティがある」と誤解しうる（軽微）。
- 使い分けの最終節で、`remember` と `rememberSaveable` のどちらを選ぶかの基準が明示されない（冒頭の入力欄の例で暗示されるだけ）。

### 3. 過剰変換・指示違反
- 分量・見出し数（H2 が4つ）・コード数（3つ）・事実1〜7 はすべて満たしている。
- タイトル「画面を回しただけで消える値」が brief のテーマ（`remember`・`rememberSaveable`・`ViewModel` の使い分け）を示しておらず、検索性も低い。
- 冒頭の「原因は一つとは限らない。」という前振りが、最後まで明示的に回収されない（回転／プロセス終了／ユーザーによる終了の3つに暗に対応しているが、そう書かれていない）。
- 冒頭で入力欄を題材にしながら、`TextField` のコード例がない（例は Counter と Form で、Form には UI がない）。
- 締めの「その期待自体を見直す番である。」は修辞が強く、やや説教調。
- `SavedStateHandle` のコード例がないので、事実7の実践面が薄い（違反ではない）。

### 4. 判断：修正後に公開
最も重要な修正：`listSaver`／`mapSaver` の説明を正す（「保存したい形」ではなく「値をリストで持つか、キー付きのマップで持つか」の違いだと書く）。あわせて、タイトルをテーマが分かるものにする。

## Y

### 1. 読みやすさ：4/5
「仕組みごとに1節、最後に共通前提と判断基準」という教科書的な構成で、対象読者が迷わず読める。日本語も自然。ただし冗長で、同じ内容の言い換えが多い（「無力」「万能ではない」「筋が悪い」など）。

### 2. 技術的正確性：4/5
3つのコードはいずれも正しい（`savedStateHandle.getStateFlow` と setter の使い方も正しい）。問題になりうる箇所は次のとおり。

- 「消えても構わないなら `remember`、ユーザーが再びアプリを開いたときにも残っていてほしいなら `rememberSaveable` か `ViewModel`（＋ `SavedStateHandle`）」：事実8と衝突しうる。「再びアプリを開いたとき」は、ユーザーがアプリを閉じた後の再起動とも読める。その場合 `rememberSaveable` も `SavedStateHandle` も復元されないので、読者が永続化（DataStore や Room）の代わりにこれらを選ぶ誤りを招く。正しくは「バックグラウンドから戻ったとき（プロセス終了後の復元を含む）」。
- 「3つの仕組みには、共通する一つの前提がある。…`rememberSaveable` の値も `ViewModel` も復元されない」：「3つ」と言いながら、中身は2つについての記述になっている。`remember` はそもそも回転でも消えるので「共通前提」という整理がずれている。
- 「`ViewModel` が内部に持つ `SavedStateHandle`」：直後のコードでは正しくコンストラクタ注入しているが、本文の「内部に持つ」は不正確（軽微）。
- 「`ViewModel`：…プロセス終了には無力」：`SavedStateHandle` を使えば対処できると本文で述べており、見出しの断定が強すぎる（軽微）。

### 3. 過剰変換・指示違反
- **分量超過**：コード除外で約2,500〜2,690字あり、上限2,500字程度を超えるか上限ぎりぎり。H1 が長く、冒頭の導入と末尾の段落が冗長。
- 見出しは H2 が5つで上限いっぱい。「共通して覚えておきたい前提」は1段落だけの節で、独立させる必要が薄い。
- 「大きなリストや画像データのようなものをここに保存しようとするのは筋が悪い。」「View システム時代の感覚を引きずったままでも大きく判断を誤ることは少ないはずだ。」は評価語や含みが多く、情報が増えていない。後者は、冒頭の「View の経験が逆に迷わせる」という前振りを「引きずったままでもよい」で閉じており、主張がずれている。
- 導入の「`onSaveInstanceState` や `ViewModel` のような馴染みのある仕組み」は良い橋渡しだが、本文で `onSaveInstanceState` と `rememberSaveable` の対応は明示されない（未回収）。
- 事実1〜7 はすべてある。

### 4. 判断：修正後に公開（3本の中で最も公開に近い）
最も重要な修正：結びの判断基準の「ユーザーが再びアプリを開いたときにも残っていてほしいなら」を「バックグラウンドから戻ったとき（プロセス終了後の復元を含む）」に直し、ユーザーによる明示的な終了では残らないことと整合させる。あわせて2,500字以内に削る。

## Z

### 1. 読みやすさ：3/5
事実を一つずつ丁寧に積み上げていて、文は平明。一方で事実シートを順に言い換えた印象が強く、`remember` の説明が「保持し損なうもの」と「変更を伝える」の2節に割れていて、読者が最初に知りたい「なぜ数字が増えないか」が後回しになる。最後はまとめの見出しがないまま、役割分担の段落で唐突に終わる。

### 2. 技術的正確性：2/5
- **「入力欄の一文字ごとの値やスクロール位置は前者に、サーバーから取得した一覧やユーザー操作の結果として組み立てるドメインの状態は後者に、それぞれ置き場所が決まる。」**：前者／後者が逆。直前の文は「…は `ViewModel` へ置き、…は `remember` や `rememberSaveable` へ置く」の順なので、前者＝`ViewModel`、後者＝`remember`/`rememberSaveable` となる。この文のままでは「スクロール位置は ViewModel、サーバーの一覧は rememberSaveable」と読め、事実6・10と正反対の選択を読者にさせる。記事の結論部分にある致命的な誤り。
- 「Jetpack Compose の入力欄やスクロール位置は、コンポーザブル関数の外に保存場所を持たない限り、再コンポーズのたびに初期値へ戻ってしまう。」：誤解を招く。`remember` を使えば再コンポーズを越えて保持されるので（事実1）、「関数の外に保存場所が必要」という冒頭の主張は本文と矛盾する。
- 「View システムでは Activity や Fragment のフィールドに値を持たせれば済んだ」：不正確。View でもフィールドは回転やプロセス終了で失われ、`onSaveInstanceState` や `ViewModel` が必要だった。対象読者の経験と食い違う。
- 「公式ガイドが示すこの考え方に沿えば、状態ごとにどちらへ置くかを個別に悩む必要はない。」：言い過ぎ。境界事例（フォームの入力値を ViewModel に持つかなど）は実務で普通に悩む。
- コード2つは断片（`@Composable` 関数の外）だが、説明用としては許容範囲で、挙動も記述どおり。

### 3. 過剰変換・指示違反
- 分量（約1,850〜1,980字）、見出し（H2 が4つ）、コード2つ、事実1〜7 は形式上満たしている。
- 事実シートを言い換えて並べただけの文が多い（例：「`remember` は、コンポーザブルが再コンポーズされても値を保持する。ただし、そのコンポーザブルがコンポジションから外れると値は破棄される。」は事実1とほぼ同文）。記事としての付加価値が薄い。
- 「これら二種類の再生成」「二種類の再生成のいずれにも対応する」という独自の言い方がやや硬く、プロセス終了を「再生成」とまとめるのは用語として曖昧。
- `ViewModel` のコード例がなく、まとめの節もない。

### 4. 判断：このままでは公開不可
最も重要な修正：最終段落の前者／後者の逆転を直す（代名詞をやめ、「スクロール位置は `rememberSaveable`、一覧は `ViewModel`」と名指しで書く）。あわせて冒頭の2文（関数の外に保存場所が必要、View ならフィールドで済んだ）を正す。
