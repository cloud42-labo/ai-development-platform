## P

### 1. 読みやすさ: 3/5
導入の「回転させた途端0に戻る」という具体的な場面はつかみとして効いている。ただ「〜に尽きる」の多用、「サイズの見積もりも甘くない」「一見、辻褄が合わない話に見えるかもしれない」のような演出が多く、論旨の流れを何度か止めている。

### 2. 技術的正確性: 2/5
- 「システムによるプロセス終了に対しては、`ViewModel` も他の手段と同じく無力だ。」: **誤り**。直前の節で `rememberSaveable` はプロセス終了後の復元を越えると説明しており（事実4）、「他の手段と同じく」はこれと矛盾する。読者は `rememberSaveable` もプロセス終了で消えると受け取りかねない。
- 「消えても構わないなら `remember`、次にアプリを開いたときにも残っていてほしいなら `rememberSaveable` か `ViewModel`（＋ `SavedStateHandle`）」: **誤解を招く**。事実8のとおり、ユーザーがアプリを閉じた後に開き直しても値は復元されない。これは前の節で本文自身が述べていることでもある。この書き方では、永続化（DataStore/Room等）が必要な場面で `rememberSaveable` が選ばれてしまう。
- 「画面が生きている間は消えてほしくない UI 状態（入力中の文字列、スクロール位置など） → `rememberSaveable`」: **誤解を招く**。「画面が生きている間」なら `remember` で足りるように読める。`rememberSaveable` を選ぶ理由（構成変更・プロセス終了後の復元を越える）が落ちている。
- 「違うのは、置き場所がコンポーザブル関数の中か、`ViewModel` の中かだけだ。」: **言い過ぎ**。生存スコープ（コンポジションから外れたときの扱い、画面間の共有可否）も違う。「だけ」と断定すると、使い分けの判断材料を削ってしまう。
- 「判断の軸は一つでいい——このコンポーザブルが消えたとき、この値はどうなってほしいか」: 直後の基準に「他の画面からも参照したいなら」が入っていて、軸が一つではない。自己矛盾している。また `rememberSaveable` の値も、通常はコンポーザブルがコンポジションから外れると破棄される。そのため、この問いに `rememberSaveable` を答えとして割り当てるのは不正確。
- 「三つの違いは、機能の多さではなく、値が生き残る範囲の違いに尽きる。」: **言い過ぎ**。事実10の軸（画面をまたぐか、ビジネスロジックが絡むか）が抜けている。
- 「`remember` がどこまで面倒を見てくれるかは、そのコンポーザブルがコンポジションに乗っている間、という一言に尽きる。」: 直後に構成変更・プロセス終了でも消えると補足しているので実害は小さい。ただ「一言に尽きる」と言い切った後に条件を足しており、記述が揺れている。
- 「「この値が変わったら再描画してほしい」」: 事実2の用語は「再コンポーズ」。描画フェーズと混同させる。
- 「しばらく裏で放置されただけで」: プロセス終了は時間経過ではなくシステムのメモリ回収で起きる（事実3）。曖昧な表現。

### 3. 過剰変換・指示違反
- 無理のある修辞: 「サイズの見積もりも甘くない」（日本語として不自然。「甘く見てはいけない」の意図と思われる）、「一見、辻褄が合わない話に見えるかもしれない。…あれほど頑丈に作られていたはずだ」（読者に誤解を植え付けてから否定しており、不要）、「三つがそろって手放す一線」（見出しが「三つ」なのに、本文が挙げるのは `rememberSaveable` と `ViewModel` の2つだけ）。
- 回収されない前振り: 「判断の軸は一つでいい」と置いたのに、基準は3軸になっている。
- ニュアンスの欠落: 使い分けの根拠が「公式ガイドの考え方」であること（事実10）がViewModel節にしか出てこない。まとめは筆者自身の判断基準に置き換わっている。
- 導入の論理: 「View システムで…使い分けに慣れていた開発者ほど、この落差に戸惑う。…3つの道具に分かれて見えるからだ。」は、回転で値が消える現象と「道具が分かれて見える」ことの因果がつながっていない。
- 字数がわずかに超過（約2,560字）。

### 4. 判定: 修正後に公開
**最重要の修正**: 「`ViewModel` も他の手段と同じく無力だ」を、`rememberSaveable` と対比する正しい記述に直す。あわせて、まとめの「次にアプリを開いたときにも残っていてほしいなら」を「構成変更やプロセス終了後の復元を越えて残したいなら」に改め、明示的に閉じた場合は復元されないことと矛盾しないようにする。

## Q

### 1. 読みやすさ: 4/5
平明で論旨の順序が素直。各節が「何ができるか → 何に弱いか」で揃っていて追いやすい。結びの一文が長く、「View システム時代の感覚を引きずったままでも」が文意をぼかしている点がやや惜しい。

### 2. 技術的正確性: 3/5
- 「消えても構わないなら `remember`、ユーザーが再びアプリを開いたときにも残っていてほしいなら `rememberSaveable` か `ViewModel`（＋ `SavedStateHandle`）」: **誤解を招く**。これはP・Rと同じ問題で、事実8（明示的に閉じた場合は復元されない）と、本文の「共通して覚えておきたい前提」節の両方に矛盾する。永続化が必要なケースで誤ったAPIを選ばせる。
- 「迷ったときは「この状態は、この画面のこのコンポーザブルが消えたらどうなってほしいか」を自問するとよい。」: `rememberSaveable` の値も、通常はコンポーザブルがコンポジションから外れると破棄される。この問いで `remember` と `rememberSaveable` は切り分けられない。
- 「…という順に絞り込んでいけば」: 3択を並べているだけで「順」になっていない。軽微な曖昧さ。
- 「それ以外の、再コンポーズの間だけ保持できれば十分な一時的な値 → `remember`」: 「再コンポーズの間」は「再コンポーズをまたいで（コンポジションに乗っている間）」の意と思われるが、言い回しが曖昧。
- それ以外は事実シートと整合している。ViewModel節の「プロセス終了に対しては無力」は `ViewModel` 単体の記述なので正しい。

### 3. 過剰変換・指示違反
- 回収されない前振り: 導入の「具体的なシナリオに沿って整理する」に対し、本文のシナリオは回転・画面遷移の言及程度で、シナリオ主導の構成になっていない。
- 字数が3本で最も超過している（約2,630字）。「これは公式ガイドが示す考え方でもある」と結びの長文を削れば収まる。
- 過剰な修辞は少ない。「筋が悪い」はやや口語的だが許容範囲。

### 4. 判定: 軽微な修正後に公開
**最重要の修正**: まとめの「ユーザーが再びアプリを開いたときにも残っていてほしいなら」を、「構成変更やプロセス終了後の復元を越えて残したいなら」に直す（明示的に閉じた後も残す必要がある値は永続化の話であり、この3つの範囲外だと一言添える）。

## R

### 1. 読みやすさ: 4/5
Qとほぼ同等に平明。導入の「その違いを取り違えると、残っていてほしかった値が消える」で記事の目的が一文で示されていて、締まりがよい。まとめの「軸は次の三つに絞られる」は、軸ではなく分類を並べているので少し引っかかる。

### 2. 技術的正確性: 2/5
- 「ただし、システムによるプロセス終了に対しては `ViewModel` も他の手段と同じく値を保てない。」: **誤り**。Pと同じで、`rememberSaveable` はプロセス終了後の復元を越える（事実4、本文の前節）。「他の手段と同じく」がこれと矛盾し、読者に `rememberSaveable` もプロセス終了で消えると思わせる。
- 「消えても構わないなら `remember`、次にアプリを開いたときにも残っていてほしいなら `rememberSaveable` か `ViewModel`（＋ `SavedStateHandle`）」: **誤解を招く**（P・Qと同じ）。事実8、および本文の「共通して覚えておきたい前提」節と矛盾する。
- 「迷ったときは、「このコンポーザブルが消えたら、この状態はどうなってほしいか」を自問するとよい。」: Qと同じで、この問いでは `remember` と `rememberSaveable` を切り分けられない。
- 「軸は次の三つに絞られる。」: 並んでいるのは判断軸ではなく配置先の分類。軽微。
- 「それ以外の、再コンポーズの間だけ保持できれば十分な一時的な値 → `remember`」: Qと同じ曖昧さ。

### 3. 過剰変換・指示違反
- 過剰な修辞はほぼない。見出し「構成変更を越えるが、プロセス終了時は消える」は正確。
- ニュアンスの欠落: まとめから「公式ガイドの考え方」への言及が消え、事実10の出典づけはViewModel節の一か所だけになっている（指示違反ではない）。
- 字数がわずかに超過（約2,540字）。

### 4. 判定: 修正後に公開
**最重要の修正**: 「`ViewModel` も他の手段と同じく値を保てない」から「他の手段と同じく」を削る。そのうえで「`remember` と同様に失われるが、`rememberSaveable` とは違って」と対比を明示する。まとめの「次にアプリを開いたとき」も、Qと同じ方針で直す。
