# Notion Status → Task Time Events → Google Sheets projection

## Purpose

Automate Task-level effort recording without creating a second operational source of truth.

**Authoritative operational records remain in Notion:**

- `Stories & Tasks` is authoritative for Task state, assignment, completion evidence, and completion status.
- `Task Time Events` is authoritative for Actor start/end intervals.
- Google Sheets is a **derived projection for aggregation and analysis only**. It is never a completion gate or an authoritative effort ledger.

Flow:

`Notion Stories & Tasks change` → `Apps Script time-driven poll (last_edited_time cursor)` → `Notion Task Time Events (authoritative)` → `Google Sheets projection`

There is **no webhook, no public endpoint, and no receiver credential** anywhere in this integration. The reconciler is driven by a time-based trigger inside the bound Apps Script project and reads Notion over the authenticated API. See **Why there is no webhook receiver** below for the reasoning and the constraint it comes from.

## Behavior

- Each run asks Notion for `Stories & Tasks` pages whose `last_edited_time` is at or after the stored cursor (minus a fixed overlap), oldest first, and reconciles each one. The very first run (no cursor yet) additionally bootstraps every currently `Status = In Progress` Task directly, regardless of `last_edited_time` — see **Behavior of the cursor** below.
- **`Type = Story` pages are excluded from Time Event generation entirely (BUG-ADP-TTE-01).** A Story is a rollup over its own child Subtasks/Tasks, not an execution unit — real effort is timed on the children, never on the Story page itself. A Story never opens a new Time Event no matter what `Status` reads (including `In Progress`, its ordinary state for as long as child work is in flight, routinely days), and its own `Done` transition needs no Time Event evidence and never reaches the Done gate. The reconciler's only remaining job for a Story is cleanup: **every** Time Event a Story accumulated before this exclusion existed gets **archived** (removed from every live view/rollup, not merely closed — see below) rather than left to linger — a closed legacy event, not only a still-open one, since a Story usually has already left `In Progress` by the time this runs (most Stories don't sit `In Progress` forever) and its bogus event was closed through the ordinary generic path just like an executable Task's. This scoping keeps a Story's own In-Progress dwell time out of Active hour totals, without introducing a second event-classification scheme for ordinary Tasks. `Type` is part of the reconciliation snapshot hash (`authoritativeSnapshotId_`) precisely so a page edited *to* `Type = Story` is never mistaken for an already-processed duplicate before `reconcileStoryTask_` gets a chance to archive its events. On an **existing live deployment**, a Story that has already been sitting `In Progress` since before this revision was deployed will not be revisited by the ordinary poll's bootstrap (which only ever runs once) until some unrelated future edit touches it, and a Story that already left `In Progress` won't be revisited by anything at all until it happens to be edited again — see `backfillStoryExclusion_()` below to archive every Story's Time Events promptly instead of waiting on either. A stray event is **archived rather than closed** deliberately: closing it would stamp a real `Ended At` and let `Duration (h)` compute over however long it happened to be open (routinely days), leaving one large but entirely fictitious interval that would still inflate every historical Active-hour aggregation this reconciler does not directly control — exactly the double-counting this exclusion exists to stop, just moved to a one-time entry instead of prevented. Archiving also means Notion's own queries exclude it going forward by default, so it stops appearing in any future poll without extra bookkeeping, and the row remains recoverable from Notion's trash. Archiving a Story's event also purges its row from the Sheet `Time Events` projection outright, not just Notion — an already-projected row (e.g. one with `Duration (h)` already computed, for a legacy closed event) would otherwise never be revisited (archiving removes it from the very query `syncTaskProjection_` uses to decide what to update), and the `Summary` tab's own actor totals and open-event counts are derived from this same projection, so a stale row there would keep feeding it the identical double-counting. `archiveStoryTimeEvent_` purges that Sheet row **before** archiving the event in Notion, not after — the two are separate remote writes, not one transaction, so an interruption (Apps Script terminated, or the Sheet write itself failing) between them must leave something a retry can still finish; purging first means a retry that reaches the still-unarchived event again (still visible in `queryNotionTimeEventsForTask_`, since the Notion archive never happened) simply re-attempts the already-idempotent purge and then the archive, whichever order the interruption landed in.
- **A page reclassified from `Type = Story` to an executable Task/Subtask does not trust its own `Started At` when opening that Task's first Time Event**, even though it otherwise would (see the "prefer the Task's own current `Started At`" behavior below). A Story carries no Time Event history of its own by the time it is reclassified — every event it ever accumulated was archived by the cleanup above, and an archived page never resurfaces in a query — so the reconciler would otherwise see empty history and treat this exactly like a genuinely brand-new Task, trusting `Started At` unconditionally. But a Story can sit `In Progress` for days before conversion, and `Started At` still reflects when it first went `In Progress` **as a Story**, not when its executable Task life began; trusting it would attribute that entire prior Story interval to the new Task the moment its first event opens. The reconciler detects this from its own Sync Log — the durable record of what it observed every page's `Type` as on every prior poll, via **any** of the outcome markers `reconcileStoryTask_` can ever write (`story_excluded`, `skipped_ambiguous_pre_upgrade_provenance:`, `closed_task_era_at_story_conversion:`, `skipped_pending_provenance_backfill:`, `archived_story_event:` — checked as a substring anywhere in a possibly multi-event, comma-joined outcome, not only its first segment) — and falls back to the observed edit time of the reclassification itself instead. Recognizing all five, not only `story_excluded`/`archived_story_event:`, matters since round 19/20: a changed Story with pre-existing events now commonly logs one of the other three, and a Story whose most recent Sync Log row happened to be one of those was otherwise invisible to this check — Codex-reported gap (round 22). This Sync Log check only runs when the Task's own `Started At` would otherwise already look fresh enough to trust by the ordinary freshness check below (at or after every other timestamp already on file), not on every ordinary Task open — both because most Task opens were never a Story and would otherwise re-scan the Sync Log's unboundedly-growing history for nothing, and because the check can only ever change the outcome in that one case: if `Started At` already looks stale, `startAt` already correctly falls back to the observed edit time regardless of what the Sync Log says. Gating on that (rather than on the Task's event history being empty, an earlier version of this gate) also closes a real gap — Codex-reported gap (round 21): a page's event history being non-empty doesn't by itself prove the risk is gone. A page can carry a genuinely older, unrelated closed Task-era event from a completely separate earlier execution (never empty, so the old "history is empty" gate never fired) and *still* be reused as a Story and converted back later — the Story spell's own freshly-recorded `Started At` can easily read newer than that old, unrelated history, which is exactly the scenario this check exists to catch. Gating on freshness instead of emptiness catches this too, while still skipping the Sync Log scan for the same vast majority of ordinary opens the old gate was written to spare. The Story-history marker itself never expires on its own, but is naturally superseded once a page's own first post-conversion execution is observed and closes a real Task-era event: any later, non-Story Sync Log row for that page becomes the new "most recent" observation, and a subsequent reopen correctly trusts a fresh `Started At` exactly like any other Task's reopen (see the freshness check below) rather than staying suppressed by Story history that no longer applies. The distrust is further narrowed to only apply when the page's **single most recent Sync Log row overall** (Story-marked or not) is itself a Story-marked one that also recorded `Status = In Progress` at that same poll — not merely the most recent *Story-marked* row taken in isolation. A page reclassified while idle (`Ready`/`Backlog`) and only later beginning its actual first execution has a `Started At` freshly (re)recorded for that later execution, unrelated to the old Story history, and is trusted normally; a later, ordinary-Task-path observation of that idle state (any Status) becomes the new "most recent" row and clears the carryover on its own, even though it isn't itself a Story marker. Only a page whose single most recent observation, period, is itself a Story-marked `In Progress` row still carries an un-refreshed, genuinely stale Story-era `Started At`. Gating on freshness rather than emptiness (round 21) does mean the Sync Log scan now runs on every ordinary, legitimate Task restart too, not only a page's first-ever event — a real widening of how often this function is called. Looks the Task ID up via `Range#createTextFinder(...).findAll()` on the Sync Log's Task ID column, the same mechanism this script already uses for `hasProcessedSnapshot_` and the Sheet-projection row lookup, rather than reading row data into the script's own memory at all. Two earlier attempts both still paid a real Sheets-transfer cost proportional to the log's size: round 23 scanned an already-fully-materialized rows array backward in JS but still fetched the entire log in one `getRange(...).getValues()` call regardless, and round 24's bounded tail chunks (walked newest-first, each chunk scanned backward for the first match) fixed that only for a Task ID that actually has a Sync Log row on file — the single most common caller of this function, an ordinary Task's very first Time Event, by definition has no row for its own ID yet, so every chunk down to the very first still had to be read before concluding "no match" — Codex-reported gap (round 26). `findAll()` runs the search on Sheets' own servers and returns match positions only, so a page that has never once appeared in the log resolves in one inexpensive round trip regardless of how large the log has grown, and a page that has appeared needs only that same one call plus a single-row read of its most recent match.
- **The reverse transition — a genuine executable Task/Subtask reclassified to `Type = Story` — never erases the Time Events it legitimately accumulated while it really was a Task.** The cleanup described above (archiving every Time Event a Story-typed page has) exists for pre-fix bogus stray data, not for real work: **per individual event**, not per page — an event whose own Note carries an immutable `Task Origin=` marker holding an explicit, non-`Story` Type value is genuine history, however the page is currently typed. For such an event, an open Time Event is **closed** at the conversion boundary (exactly like any other Task leaving `In Progress`, preserving its real duration) rather than archived, and an already-closed one is left completely untouched — neither is ever archived away. `Task Origin=` is stamped exactly once, at the event's creation (`createNotionTimeEvent_`, holding the page's Type at that exact moment), and never touched again by any later write to that same event (a close, a reassignment, ...) — deliberately kept separate from the event's ordinary, mutable `Snapshot=` field (which reflects whichever poll most recently touched the event at all, for other purposes like the Sheet projection's own audit column). Reusing that mutable field for Task-era provenance is self-defeating: `reconcileStoryTask_`'s own close of a genuine Task-era event, at the moment of conversion, stamps a *new* `Snapshot=` (this exact Story-typed poll's own snapshot) that would overwrite the very evidence that just correctly classified the event — poisoning any *later* re-observation of that now-closed event into archiving it after all, undoing the preservation. `Task Origin=` cannot be overwritten this way, and is protected from `appendNote_`'s length-based eviction the same as `Execution=`/`Boundary=`. It holds the Type value directly, not a cross-reference to anything else — a single, self-contained write with nothing else to keep in sync. `createNotionTimeEvent_` stamps a fallback `unset-type` sentinel (`NO_TYPE_MARKER`) instead of the Task's raw Type whenever that Type reads blank — Codex-reported gap (round 17): `buildNote_` only ever writes a field it receives a truthy value for, so passing the blank Type straight through silently omitted `Task Origin=` from the Note entirely, making a genuinely-new, directly-observed event indistinguishable from a pre-existing event that never got a marker at all, even though this script witnessed its creation firsthand and knows for certain the page was not `Story` at that moment. `NO_TYPE_MARKER` is a confirmed, non-`Story`, non-ambiguous value like any other Type string, so `eventWasTouchedDuringTaskExecution_` treats it identically to `Task`/`Subtask`/etc. This whole mechanism is deliberately per-event rather than "was the page ever seen as Task": a page can be observed as an idle Task (e.g. `Status = Ready`) without that observation ever touching a specific pre-existing event's own Note at all (nothing open to close, nothing new to open) — proving the *page* was once seen as Task proves nothing about whether *that particular event* was itself created during that window. An event without a confirmed `Task Origin=` (no marker at all, or the `ambiguous-pre-upgrade` sentinel — see the backfill below) gets the archive treatment described above instead, since a genuinely pre-fix bogus Story stray event has the identical no-confirmed-marker signature and this is the conservative default that protects against reintroducing the double-counting this exclusion exists to stop — **except that the archive path itself only ever runs once `taskOriginBackfillComplete_()` is true** (see `backfillTaskOriginProvenance_` below): on an existing live deployment, the already-installed `pollTaskChanges` trigger keeps running the moment this revision's code is deployed, independent of whether an operator has run that backfill yet or whether it has finished draining — Codex-reported gap (round 19). A marker-less event reached before the backfill ever marks it is otherwise indistinguishable, from the event's own data alone, from the exact race Codex flagged: archiving it before the backfill had a chance to flag it ambiguous would permanently erase the same genuine Task-era history the whole mechanism protects, just via a timing race instead of a caller reasoning about current Type. Until that flag is set, a marker-less event is treated exactly like an ambiguous one — `skipped_pending_provenance_backfill:<event ID>`, not archived. A fresh deployment never reaches this branch at all regardless of the flag, since `createNotionTimeEvent_` always stamps a marker on every event it ever creates. **On an existing deployment that actually follows the documented upgrade order, this archive branch is realistically unreachable for any genuinely pre-existing event** — Codex-reported gap (round 20): `TASK_ORIGIN_BACKFILL_COMPLETE` only ever becomes true once `backfillTaskOriginProvenance_()` has fully drained, and that same completion pass, by definition, has already stamped `ambiguous-pre-upgrade` onto every marker-less event it found along the way — so by the time the gate opens, nothing marker-less from before this deploy is left for it to act on. What remains archivable is narrower than the name suggests: a Time Event this script itself never got a chance to mark, such as one added directly in Notion (not through this script) after the backfill has already drained once. See "Known limitations".
- `Status = In Progress` (on any non-`Story` Task) ensures exactly one authoritative open Task Time Event for the currently mapped `Assigned Agent`.
- Moving from `In Progress` to `Review`, `Blocked`, `Ready`, or `Backlog` closes every authoritative open event for the Task, regardless of current assignee.
- Changing or clearing `Assigned Agent` while the Task remains `In Progress` closes the old Actor event and opens the new Actor event when the new assignment maps to a supported Actor.
- Duplicate open events for the same Task/Actor are reconciled to one open event.
- `Done` is a **completion gate, not a stop trigger**. Reconciling a Done Task never closes a Time Event after completion.
- Done with an open Time Event is rejected by restoring `In Progress`; Done with closed timing but missing an applicable Time Event, `Result`, or `Completed At` is rejected by restoring `Review`. "Applicable" means a closed Time Event whose `Started At` is at or after the Task's current `Started At` — a closed event left over from a prior, already-completed execution does not, by itself, satisfy Done for a later reopen.
- The Task's `Started At` must itself look fresh before it can identify "the current execution" at all: it must be at or after every event already on file for the Task that does not belong to the current execution. A reopened Task whose `Started At` was never actually updated (Notion does not clear it, and a later event naturally still starts *after* that stale marker regardless) is rejected as `stale_task_started_at`, rather than letting an untouched marker rubber-stamp whatever event happens to close next. A single execution can produce more than one closed event — an in-progress reassignment (including an assignee being cleared and only later reassigned, which can leave a real time gap with no open event in between) closes the outgoing actor's event, and a duplicate open event is closed by the reconciler's own duplicate-cleanup — neither ever ends an execution, only leaving `In Progress` does. **Membership is decided primarily by an explicit `Execution=` identifier**, not by timestamp ties or Reason markers: every Time Event is stamped at creation (see `createNotionTimeEvent_`) with the execution it belongs to — a reassignment replacement inherits the outgoing event's own `Execution=` unchanged (reassigning never starts a new execution) **except when the outgoing event's provenance is ambiguous** (see `eventProvenanceIsAmbiguous_`) — Codex-reported gap (round 29): an ambiguous open event can genuinely carry a real `Execution=` value, from a script era that stamped `Execution=` before `Task Origin=` tracking existed (`appendNote_` preserves it untouched across the later ambiguous backfill), and the original check for this whole "restart instead of continuing" treatment only ever examined the most-recently-started **same-actor** open event — an ambiguous event under a *different* actor than the newly desired one fell straight into the ordinary reassignment path instead, inheriting that unverifiable, possibly-Story-era identity onto otherwise-current, genuinely valid work. Such an event is now restarted (`Reason=ambiguous_provenance_restart`, the same clamp-to-its-own-Started-At as the same-actor case) regardless of which actor bucket it falls into, and never contributes its `Execution=` to the replacement's identity — falling through to the same no-`Execution=`-inherited fallback described just below, as if it predated the field entirely. — or, when the outgoing event predates this field entirely (a live deployment upgraded mid-execution) and so has no `Execution=` to inherit, gets **no `Execution=` marker at all**, deliberately: an earlier version backfilled the Task's own current `Started At` here instead, but nothing at that call site can verify `Started At` still reflects this exact, still-open execution rather than having independently drifted (a data-entry edit, or the same invisible-reopen risk the paragraph below guards against) — and a *mismatched* `Execution=` is worse than none, since the override described below authoritatively excludes a mismatch even when the legacy heuristic would have correctly kept the event in, turning a self-inflicted, unverifiable mismatch into Done wrongly blocked later for an execution that never actually reopened (see the "Known limitations" backfill precedent below, which hit the identical dilemma at a different call site). The interval's own computed start is never used for the identity here either — it is deliberately the reassignment boundary in this branch, not the execution's true start (see the opening-timing fix above), and stamping it as the identity would tag the replacement with a value that will almost never match the Task's own Started At once it closes. Only the true first-ever-open case (no outgoing event at all) uses the interval's own computed start as the identity, which already correctly falls back to the observed edit time instead of a stale, never-refreshed `Started At` (so a governance violation still gets a fresh, distinguishing identity rather than silently inheriting the old one) — the Task isn't already open in that case, so its raw Started At can't be trusted as "this same ongoing execution" the way it can mid-execution, and there is no outgoing event's Reason marker to fall back on instead. An event is current if and only if its `Execution=` exactly equals the Task's own current `Started At` — no ties, adjacency, or Reason inference needed at all, and so none of the coincidental-tie ambiguity `last_edited_time`'s minute granularity can otherwise create (two genuinely different executions' closes landing on the identical `Ended At`, which several rounds of Reason/Boundary/tie-seed heuristics could never fully close). This overrides whatever the legacy heuristic below concludes for such an event. **Only an event with no `Execution=` marker at all — data from before this field existed — falls back to the legacy heuristic**, described here for that case: membership is decided by each closed event's own `Note` markers, not by timestamp adjacency; the seed is every closed event sharing the single latest `Ended At` on the Task (a tie — more than one event can close at the exact same observed moment, e.g. a simultaneous reassignment — and every member of that tie is exempt from counting as prior evidence, never just one arbitrarily chosen "most recent" one; it is the candidate applicable evidence this whole check exists to validate, never evidence against itself) **except an event explicitly, retroactively marked `Boundary=left_in_progress`** (see below) — `last_edited_time` is minute-granular, so a genuinely prior execution's own boundary close and the current execution's fresh close can coincidentally land on the exact identical recorded `Ended At` by pure chance, not just a true simultaneous multi-event close, and that marker's entire purpose is a strong, deliberate claim ("this is confirmed to be where a past execution genuinely ended") that a mere timestamp tie must never override. A plain `left_in_progress` close with no such marker stays tie-seedable regardless: that is the ordinary, ambiguous case (e.g. a Task first observed after leaving `In Progress` with multiple open events, all genuinely closed together in this same call) the tie rule exists to handle in the first place, and `Boundary=` is never stamped on it. Beyond the seed, an event closed `reassignment` or `duplicate_reconciliation` is *also* part of the current execution — unconditionally, however far its own `Ended At` sits from the seed (an assignment gap, or a duplicate detected well after the fact, are exactly this; timestamp adjacency alone is not a sufficient signal, since a genuinely prior execution's own closing event *can* coincidentally touch a later, separate execution's opening `Started At`, which a purely adjacency-based chain would wrongly absorb) — **unless that same event also carries a retroactive `Boundary=left_in_progress` marker**, in which case it is prior-execution evidence despite its `Reason=`. That marker exists because a `reassignment`/`duplicate_reconciliation` close never by itself signals that an execution ended (only leaving `In Progress` does) — so a Task that left `In Progress` with nothing open to close (the only open event having already been closed earlier that same poll by a reassignment, say) would otherwise leave no signal at all that the execution genuinely ended there, letting a real prior execution's reassignment-only closed event go on looking "current" forever, including across a later reopen. `reconcileAuthoritativeTimeEvents_` stamps this marker itself, retroactively, on the most-recently-closed event whenever it observes a Task with zero open events outside `In Progress`/Done **and** that event's own `Reason=` is `reassignment` or `duplicate_reconciliation` — the one case that actually needs it. This stamp deliberately never backfills `Execution=`, even when the event predates that field entirely (legacy data) and has none to lose: an earlier version did, from the Task's own current `Started At`, specifically to save a legacy event that is genuinely the Task's own ONLY (and therefore current) execution from being wrongly excluded — but that backfill was found unsafe (it cannot be told apart, at this call site, from a Task reopened and restarted entirely inside one poll window, where the same backfill would tag a genuinely stale event as current instead) and was removed; see **Known limitations** below for the narrower, accepted gap this reopens. A plain `left_in_progress` close is deliberately never stamped, even though the same "zero open events" observation recurs on every later re-read of an already-normally-closed Task (e.g. an unrelated field being edited while it sits in `Review`): a plain `left_in_progress` close is already unambiguous prior-execution evidence by `Reason=` alone (see above) and never needed the marker, and stamping it anyway would make it look, by that same marker, retroactively prior — wrongly excluding it from the Done gate's tie-seed even when it is the genuinely current applicable event, and rejecting a legitimate Done as `stale_task_started_at`. The stamp is a side-by-side addition to the event's existing `Reason=`, never overwriting it, since both facts (why it closed, and that this is also where its execution ended) need to survive together. Anything else — a genuine `left_in_progress` close outside the seed, or no reason at all (legacy data) — stays prior-execution evidence even if it happens to coincide in time with something in the current execution.
- `Completed At` must not just be present: it must be at or after the Task's current `Started At` and at or after the applicable closed event's `Ended At`. A `Completed At` left over from a prior, already-finished execution (Notion does not clear it on reopen) does not satisfy Done for a later reopen either.
- `Result` must not just be present either — it carries no timestamp of its own to check freshness against, so instead each closed event is stamped with a fingerprint of the `Result` text that validated Done against it. If that exact text already validated a *different*, earlier closed event for the same Task, Done is rejected as stale: the text was never actually refreshed for this execution. A stamp matching the *current* applicable event is expected and fine — Done is always re-verified (see below), so an unchanged, already-validated `Result` recurs on every re-check of a still-Done Task. An event's Note can carry more than one fingerprint over its lifetime — Result can be edited more than once while a Task stays Done on the same applicable event, each edit adding its own `Result Fingerprint=` stamp rather than replacing the last — so the reuse check is against every fingerprint that event ever recorded, not only the most recent one. This check can only catch a reuse against an event it once stamped, so a Task that reached Done under an *older* Code.gs revision without this stamping feature has an unstamped applicable event, and its stale Result would go undetected by exactly one reopen. `backfillResultFingerprints_()` (an operator escape hatch, see "Behavior of the cursor") closes this for an existing live deployment being upgraded to this revision — run it once, immediately after deploying, before any already-Done Task is reopened. A fresh deploy has no pre-existing Done history and needs no backfill: every event is stamped on its own first Done pass from day one. Every write to a Time Event's `Note` field (a fingerprint stamp, or a close's `Reason=`/`End Status=` metadata) goes through a shared `appendNote_` helper that keeps the combined text within Notion's per-field limit by dropping prior metadata first, never by truncating from the end — which would risk cutting off the marker being written right now (e.g. silently corrupting a fresh Result Fingerprint stamp) rather than just losing old history. Which metadata goes first: oldest *non-fingerprint* segments (`Reason=`/`Snapshot=`/`Changed By=`/`End Status=` — only the newest of each ever matters, so losing old ones is harmless) before ever touching a `Result Fingerprint=` segment, and only the oldest fingerprint once no non-fingerprint segments remain — stale-Result detection needs every fingerprint an event ever recorded to survive as long as possible, so those are evicted last, not first.
- A Task observed as `Done` is **always** re-verified by the gate, even if its reconciliation snapshot happens to hash identically to one already processed (Notion reports `last_edited_time` at only minute granularity, so a same-minute rollback-and-retry can collide) — an invalid Done is never silently left in place because of a hash collision.
- A newly opened Time Event starts from the Task's current `Started At` whenever that is at or after every timestamp already on file for the Task — covering both a first-ever event and a reopened Task — rather than from whatever moment the poll happened to observe the edit, so a later same-window edit (e.g. a reassignment moments after restart) cannot silently drop the time before it. When the new Actor's event opens because a reassignment *just* closed the outgoing Actor's event this same call, "every timestamp already on file" also counts that reassignment's own moment even though the in-memory Task/event snapshot this call started with doesn't yet reflect the close it itself just made — otherwise an unrelated, unchanged `Started At` from *before* the reassignment would look "fresh" by comparison to a now-stale in-memory view, and the replacement Actor's event would open at the wrong, earlier moment, overlapping the outgoing Actor's own interval and double-counting effort.
- Valid completion order is: finish work → `Review` (time event closes) → record `Result` + `Completed At` → `Done`.
- Reconciliation snapshots are derived from the authoritative Notion page (`last_edited_time`, Status, Assigned Agent). Recorded interval timestamps come from `last_edited_time` on the Task, not from when the poll happened to run — this avoids polling-frequency itself distorting recorded effort, though `last_edited_time` carries its own bounded imprecision; see **Known limitations**.
- Sheet rows are upserted by the authoritative Notion Task Time Event page ID.

## Why there is no webhook receiver

The earlier design in this directory used a Notion webhook subscription. Notion proves a webhook delivery's authenticity **only** through the `X-Notion-Signature` request header, computed as HMAC-SHA256 of the raw body under the subscription's verification token.

A Google Apps Script Web App **cannot read request headers**. `doPost(e)` exposes the body, query parameters, and content type; the request headers are not in the event object, and Google has stated this will not be added. Consequently:

- Apps Script can never verify a Notion signature itself.
- The only credential an Apps Script endpoint can check is one placed in the URL or the body — a static bearer secret, which is exactly what Codex flagged as a P1 (the URL becomes a bearer credential retained in Notion configuration and browser history).
- Keeping webhooks therefore requires a **separate relay service** that can read headers, plus a second shared secret to authenticate the relay's own hop into Apps Script.

The relay was real work solving a real constraint, but the constraint only exists because of the webhook. This integration's reconciler never trusted webhook content in the first place: the delivery was reduced to a page ID, and every field driving a mutation was re-fetched from Notion. A delivery was only ever a "something changed, go look" ping — and Apps Script can generate that ping locally from a time-driven trigger over `last_edited_time`.

Removing the webhook removes the header problem, the relay, the relay secret, the verification-token enrollment dance, and the public endpoint, without changing what gets recorded.

Trade-off, stated plainly: reconciliation is no longer near-instant. A change is picked up within one poll interval (5 minutes by default, tunable to 1) under normal load, more under a large write-producing backlog. This delays a Done-gate rollback correspondingly, and — see **Known limitations** — the same page-level `last_edited_time` used for both detection and recorded `Ended At`/boundary timestamps carries an imprecision of its own, for a distinct reason: Notion's public API exposes no per-property change history, only one edit time for the whole page.

## Security model

The integration has no inbound attack surface: nothing outside the Apps Script project can invoke the reconciler, so there is no request to authenticate.

- **One secret, one place.** `NOTION_TOKEN` lives only in Apps Script Script Properties. There is no webhook verification token and no relay secret to generate, duplicate across systems, rotate in lockstep, or leak. Never put the token in source code, GitHub, the Sheet, a URL, or logs.
- **No public endpoint.** The project defines no `doGet` / `doPost`, and the Web App deployment is removed. An attacker who learns the script ID has nothing to call.
- **No credential in any URL.** Satisfied by construction rather than by mitigation — there is no receiver URL.
- **Notion remains the only source of operational truth.** Every mutation is derived from a page Notion returned over an authenticated call; the reconciler can only move Task Time Events toward the state Notion already holds, and repeating a pass over the same page is a no-op.
- **Least privilege on the Notion side.** The connection needs access to `Stories & Tasks` and `Task Time Events` only.

`reconcileTaskById(pageId)` exists as an operator escape hatch for E2E and debugging. It runs only from the Apps Script editor, as the project owner, and is not reachable from outside.

## Notion connection requirements

The Notion connection used by Apps Script must have access to both `Stories & Tasks` and `Task Time Events`, with capabilities sufficient to:

- read Task state, assignment, `Result`, `Started At`, and `Completed At`;
- update Task `Status` when the Done gate rejects an invalid transition;
- query Task Time Events;
- create Task Time Events; and
- update `Ended At` / `Note` on Task Time Events.

Creating Task Time Events through the Notion API requires **Insert Content** capability. Do not continue to E2E if the connection is read/update-only.

`Stories & Tasks`.`Status` is a Notion **`select`** property, not the distinct **`status`** property type — the two use identically-shaped but incompatible filter/write payloads (`{ select: { equals / name } }` vs `{ status: { equals / name } }`), and the Notion API rejects the wrong one outright as a `validation_error` rather than silently matching zero rows. Every Status filter (`backfillResultFingerprints_`, `queryActiveInProgressTasks_`) and the Done-gate rollback write (`updateTaskStatus_`) are built from the single `DEFAULTS.STATUS_PROPERTY_TYPE` constant so a real schema change only needs updating in one place. This was an actual production regression when polling replaced the old webhook receiver (which never filtered by Status at all): `pollTaskChanges` failed with HTTP 400 on the live database from day one, undetected because the test fixtures also modeled Status as the wrong property type. `test/poll.test.mjs` now asserts the literal request bodies for all four call sites against the `select` shape — see "Status property schema contract" in that file.

## Behavior of the cursor

`LAST_SYNC_CURSOR` (Script Property) holds the timestamp the next poll starts from. Each run:

- queries from `cursor - 2 minutes`, because Notion reports `last_edited_time` at minute granularity and a page can be indexed fractionally after it is written;
- **bootstraps** by additionally querying every Task currently `Status = In Progress` by Status, independent of `last_edited_time`, and merging the two lists by page ID — until that has genuinely finished, tracked by its own `BOOTSTRAP_ACTIVE_DONE` flag rather than by whether `LAST_SYNC_CURSOR` is set. Without the active-Task query at all, a Task that had already been `In Progress` for longer than the one-hour initial lookback would never receive an open Time Event, and would then permanently fail the Done gate for lack of any applicable interval once it eventually moved. Tracking completion separately from the cursor matters because the very first run sets `LAST_SYNC_CURSOR` from the incremental side regardless of whether the active-Task query itself was complete — if that query is wide enough to hit `QUERY_PAGE_SAFETY_LIMIT` and truncate, `BOOTSTRAP_ACTIVE_DONE` stays unset (and a `BOOTSTRAP_ACTIVE_RESUME_CURSOR`, sorted ascending, records how far it got) so the *next* run resumes it, instead of a cursor-coupled flag disabling the active-Task query forever after one incomplete attempt. The resumed query itself uses `on_or_after` (not a strict `after`) plus a local tie-offset skip — the same pattern as `LAST_SYNC_CURSOR_TIE_OFFSET`, tracked separately as `BOOTSTRAP_ACTIVE_RESUME_TIE_OFFSET` — so it correctly resumes within a tied timestamp instead of silently dropping the remainder of one;
- re-reads are free — the reconciler's snapshot hash (`page id | last_edited_time | Status | Assigned Agent | Type`) drops anything unchanged, reported as a `duplicate:` outcome. `hasProcessedSnapshot_` matches this against only the page's single **most recent** Sync Log row for its own Task ID, never "was this exact snapshot ever logged, at any point in this page's history" (an earlier version of this check) — Codex-reported gap (round 27): a page observed as `Task`/`In Progress`, reconciled once as `Story` (closing/archiving its open event via `reconcileStoryTask_`), and then changed back to that identical `Task`/`In Progress` state within the same `last_edited_time` minute produces a snapshot byte-identical to the *first* Task observation already on file — matching against "ever seen anywhere" found that old row and skipped this genuinely-changed final transition as `duplicate:`, leaving the page stuck `In Progress` with no open Time Event until some unrelated later edit changed the hash. Matching only the most recent row is both the correct definition of "duplicate" (nothing changed since this page was last looked at) and strictly more permissive than the old check — it can only decide to re-reconcile a page the old check would have skipped, never the reverse. **Except a Task observed as `Done`**: that hash is never trusted to skip a Done re-read, because Notion's minute-granular `last_edited_time` means a same-minute rollback-and-retry can hash identically to an already-processed attempt — Done is always re-verified by the gate;
- reconciles at most 25 Tasks **that actually do something** per run, so a large backlog of real work cannot exceed the Apps Script runtime limit. An outcome that made no Notion write does **not** count against that limit — it is skipped for free: a `duplicate:`/`ignored:` re-read, and also a *steady-state* `done_gate_passed` (an already-valid Done left exactly as it is, which the point above requires re-checking on every poll regardless). A changed `Type = Story` page's own outcome is free the same way whenever **every** action it reports made no write — `story_excluded` (nothing to do at all), and, per event, `skipped_ambiguous_pre_upgrade_provenance:`/`skipped_pending_provenance_backfill:` (see `reconcileStoryTask_`'s own "Behavior" above) — but **not** when any of a Story's (possibly several, comma-joined) per-event actions made a real write (`archived_story_event:`/`closed_task_era_at_story_conversion:`), which still costs a Notion write and still counts, the same as any other write. Recognizing the two no-write skip outcomes as free matters for the identical reason as `duplicate:`/`done_gate_passed` — Codex-reported gap (round 21): once the mandatory provenance backfill has run, a changed pre-existing Story commonly reports one of these two outcomes (see "Known limitations" on the archive path being largely unreachable for legacy data), and without this, 25 such Stories inside one poll's overlap window would exhaust the cap on pure re-skips and defer genuinely write-needing Tasks sorted behind them, for potentially several trigger intervals. This matters because the 2-minute overlap always re-includes Tasks from the previous run, and a Done Task always gets re-verified: if a dense cluster of either — duplicates, or 25+ Tasks that are legitimately already Done — were charged against the same cap as new work, that cluster (sorted first, being oldest) would be re-selected and re-processed every run, and Tasks behind it would never be reached. The *first* time an already-valid Done event is verified (nothing has stamped it with its Result's fingerprint yet — a brand-new completion, or a legacy event from before this fingerprinting existed), the gate reports the distinct outcome `done_gate_passed:stamped` and it **does** count against the cap: it makes a real write (stamping the Result fingerprint onto the Time Event, for future reopen-staleness detection), so a cohort larger than 25 first-time stamps stops at the cap like any other write-cohort rather than writing all of them in one run. A rejected Done (`done_gate_rejected:...`) also still counts — it made a real write (the rollback) and is exactly the case always-reverifying Done exists to keep catching. **There is deliberately no separate, smaller cap on free outcomes either** — an earlier version added one and it reintroduced the identical stall for a large free-outcome cohort instead of a large write-cohort. A free-outcome scan is bounded only by how many Tasks the run's own query returned, which pagination already caps at 5000 (below); a pathologically large simultaneous free-outcome cohort (a bulk edit, or hundreds of Tasks that are all legitimately Done and already stamped, sharing one timestamp) still costs a real Time Events query each, so it can make a single run slow, not just cheap — see the wall-clock bound below for why that cannot strand the cursor;
- also stops — regardless of `MAX_TASKS_PER_RUN` or how many Tasks remain — once a run has been going for `MAX_RUN_DURATION_MS` (4 minutes). Apps Script kills a run outright at its own per-execution limit (6 minutes on a consumer account, 30 on Workspace); an uncaught kill there never reaches the cursor-persist step, so a run that ran the platform out of time would lose all progress and re-scan the identical prefix on the next trigger, forever — the same indefinite stall a missing per-run cap causes, just via wall clock instead of a task count. Crossing the budget instead stops the scan early and persists the cursor at the last Task actually reconciled, exactly like hitting `MAX_TASKS_PER_RUN` does;
- each underlying Notion query (the time-window query, the bootstrap active-Task query, and the per-Task Time Events query) is itself paginated up to `QUERY_PAGE_SAFETY_LIMIT` (50 pages, 5000 rows) via a shared `paginateNotionQuery_` helper. Hitting that limit sets `truncated: true` rather than silently dropping the remainder — `pollTaskChanges` folds this into the same cursor-hold behavior as an early-stopped scan (below), so a single incremental window matching more than 5000 changed Tasks cannot cause the cursor to skip past whatever wasn't retrieved;
- advances the cursor to the moment the query was issued, but only for a run that gets through its entire batch *and* whose source query(ies) were not truncated. A run that stops early, or was truncated at the source, leaves the cursor on the last Task it actually looked at, and the next run continues from there. A failed or skipped run leaves the cursor alone entirely, so the window is retried.
- **resumes correctly when a stop lands inside a tied timestamp.** `LAST_SYNC_CURSOR` alone can only express a moment in time, not "partway through the Tasks that share that exact moment" — and Notion's `last_edited_time` is minute-granular, so a bulk edit (or many Done Tasks re-verified in the same poll minute) commonly produces a group of Tasks sharing one identical value. If a capped run (`MAX_TASKS_PER_RUN` or `MAX_RUN_DURATION_MS`) stops in the middle of such a group, the next run's `on_or_after: cursor - overlap` query returns the *entire* group again from its own start — harmless for most outcomes (an already-processed Task is a free `duplicate:`), but a Done Task is never dedup-skipped and always costs a real Time Events query to re-verify, so a tied Done cohort larger than one run's budget would otherwise be rescanned from its own start forever, never draining and never reaching whatever sorts behind it. `LAST_SYNC_CURSOR_TIE_OFFSET` (Script Property, an integer) records how many leading members of the tied-at-cursor group this run actually finished, so the next run skips exactly that many and resumes where the previous one stopped instead of restarting the tie. It resets to `0` on any run that reaches a genuinely complete end (nothing left to resume mid-tie). If a capped, truncated run's tie-offset skip covers the *entire* batch that call retrieved (nothing new to scan at all), `LAST_SYNC_CURSOR` and its tie offset are left completely untouched rather than falling through to "advance to now" — which would otherwise silently jump the cursor past whatever unretrieved data caused the truncation. (A single tied group wide enough to itself exceed the pagination safety limit — thousands of Tasks sharing one exact minute — is a separate, extreme-scale limitation this cannot fully resolve, since Notion's public API offers no secondary sort key to page within an exact-timestamp tie.)

To re-run a window deliberately, clear `LAST_SYNC_CURSOR` (the next poll then bootstraps again and looks back one hour, and any stale `LAST_SYNC_CURSOR_TIE_OFFSET` is ignored on that bootstrap run and freshly recomputed) or call `reconcileTaskById(pageId)` for a single Task. To backfill Result-fingerprint stamps onto Done Tasks that predate that feature (a live-deployment upgrade only — see the Done gate section above), call `backfillResultFingerprints_()` once from the editor; if the deployment has more Done Tasks than the pagination safety limit, it is itself resumable the same way — a truncated call persists `BACKFILL_RESUME_CURSOR` (queried with `on_or_after`, plus a local `BACKFILL_RESUME_TIE_OFFSET` skip, so a tied timestamp at the truncation boundary resumes correctly rather than silently dropping its remainder) and calling it again continues past what was already stamped instead of re-scanning the same prefix. It is also bounded by `MAX_RUN_DURATION_MS`, the same wall-clock budget `pollTaskChanges` uses: even a batch of Done Tasks well under the pagination safety limit can still run long enough to risk an uncaught Apps Script kill, since every Done Task costs a real Time Events query/write (Done is always re-verified). Hitting that bound checkpoints `BACKFILL_RESUME_CURSOR`/`BACKFILL_RESUME_TIE_OFFSET` at exactly however many Tasks this call actually got through — not however many the fetched page contained — so a call stopped by the wall clock resumes correctly on the next call, the same as one stopped by pagination truncation. When a tied cohort itself needs more than one wall-clock-bounded call to drain, the stored tie offset accumulates across calls (the count a prior call already persisted, plus however many this call newly processed while still inside that same tied timestamp) rather than each call overwriting it with only its own contribution — the latter would make every further call re-skip to the same fixed count and re-walk (never past) the same middle slice forever. The wall-clock budget also covers the pagination phase itself, not just the processing loop after it: fetching Done Tasks reserves only `MAX_RUN_DURATION_MS` minus `MIN_PROCESSING_RESERVE_MS`, leaving that reserve for actually reconciling and checkpointing whatever got retrieved — a large Done database or a slow Notion response can otherwise burn the whole budget on page fetches alone (up to `QUERY_PAGE_SAFETY_LIMIT`, each its own round trip) before the processing loop's own check ever runs, risking an uncaught kill with nothing reconciled or checkpointed at all. That reservation extends itself, within the same continuous fetch, when a resumed tied cohort's persisted `BACKFILL_RESUME_TIE_OFFSET` already exceeds what the reserved budget alone can retrieve: since the resumed query is inclusive (`on_or_after`) and always restarts from its own beginning, stopping at the deadline with zero net progress there would make every further call re-fetch and re-skip the identical already-consumed prefix forever, with nothing about the situation ever changing on its own. Rather than starting a second, independent pagination pass past that point — which would only re-fetch from the start again and waste the time the first pass already spent, since both share the same wall clock and could never net out ahead of each other — the fetch keeps going past the primary deadline specifically while the tie-offset skip would still consume everything retrieved so far, bounded by the full run budget minus `MIN_PROCESSING_RESERVE_MS` (still reserved, even on this escalated pass, so processing and checkpointing are never fully starved — see "Known limitations" below for what that reserve size itself assumes). A merely-large (not pathologically large) tied cohort can therefore still make progress instead of permanently stalling; a tied group wide enough to exceed even the full budget's own retrieval capacity remains the same extreme-scale limitation already documented above (no secondary sort key to page within an exact-timestamp tie), just reached one call later. For a very large Done backlog beyond a single pagination page, expect to call it repeatedly (from a time-driven trigger, or by hand) until its returned summary shows `truncated: false` and `timedOut: false`.

To backfill the `Type = Story` exclusion (BUG-ADP-TTE-01) onto an **existing live deployment**, call `backfillStoryExclusion_()` once from the editor immediately after deploying. It queries **every** `Type = Story` page directly — deliberately not scoped to `Status = In Progress` — and reconciles each, **archiving** (not merely closing — see "Behavior" above for why) every Time Event it has, open or already closed. Two independent gaps a `Status = In Progress` scope would miss: `BOOTSTRAP_ACTIVE_DONE` is already set on such a deployment, so the ordinary poll bootstrap (which only ever runs once) will not revisit a Story that has already been sitting `In Progress` since before this revision was deployed; and most Stories have already *left* `In Progress` by the time this runs, with their bogus event already closed (a real `Ended At`, a fictitious multi-day `Duration (h)` already computed) through the ordinary generic path — a `Status = In Progress` filter would never see that Story again to correct it. It is resumable the same way `backfillResultFingerprints_` is: archiving a Story's Time Event does not remove the Story itself from this query's own result set, so a truncated call persists `STORY_EXCLUSION_RESUME_CURSOR` (queried with `on_or_after`, plus a local `STORY_EXCLUSION_RESUME_TIE_OFFSET` skip so a tied timestamp at the truncation boundary resumes correctly) — without it, an unqualified re-run would keep re-fetching the identical oldest prefix forever and never reach Story pages beyond it. (A single tied group wide enough to itself exceed the pagination safety limit is a separate, extreme-scale limitation this cannot fully resolve — see "Known limitations".) It also bounds its own pagination phase the same way and for the same reason: fetching reserves only half of `MAX_RUN_DURATION_MS`, leaving the rest (short of `MIN_PROCESSING_RESERVE_MS`) for actually reconciling and checkpointing whatever got retrieved, so many matching Stories or a slow Notion response cannot burn the whole run just fetching pages and leave nothing processed to checkpoint. If its returned summary shows `truncated: true` or `timedOut: true`, call it again to continue past what was already handled. A fresh deploy has no pre-existing Story Time Events at all and needs no backfill — the exclusion applies to every poll from day one.

This is the one caller that bypasses `reconcileTaskPage_`'s ordinary snapshot dedup (`{ bypassDedup: true }`) — Codex-reported gap (round 23): a Time Event added directly in Notion (not through this script, e.g. by hand, after this backfill has already run once) attaches to a Story via its own `Task` relation, not by editing the Story page itself, so the Story page's own snapshot (`id | last_edited_time | Status | Assigned Agent | Type`) never changes. Without bypassing dedup, a re-run of this backfill against that same, already-once-reconciled Story would report `duplicate:` and never even call `reconcileStoryTask_` again — the new event's archival would then depend on some unrelated future edit to the Story page itself, which might never come. `reconcileStoryTask_` is fully idempotent, so bypassing dedup here only ever costs an extra, harmless re-check for a Story with nothing left to do — never a different outcome for genuinely unchanged data. No other caller (`pollTaskChanges`, `reconcileTaskById`, `backfillResultFingerprints_`) bypasses dedup; only this explicit, repeatable cleanup pass needs to.

**`backfillStoryExclusion_()` never resolves an `ambiguous-pre-upgrade` marker (see `backfillTaskOriginProvenance_` below) by archiving it — this was attempted once (round 17) and reverted (round 18) as unsafe.** The attempt reasoned that because this function only ever visits pages that *are* `Type = Story` right now (its own query filter), an ambiguous-marked event on one of those pages was safe to resolve by archiving. That repeats the exact mistake `backfillTaskOriginProvenance_`'s own entry below root-causes: a page's *current* Type never proves anything about its pre-revision event history, in *either* direction — a page reading `Story` right now may have cycled through `Task → Story` any number of times before this revision was ever deployed, so an event on it can just as easily be genuine pre-upgrade Task-era work as bogus Story stray data. There is no caller, not even one scoped to current Story pages, for which "currently Story" adds information a marker was deliberately stamped ambiguous specifically because current Type *couldn't* answer. Every caller — this backfill included — leaves an ambiguous-marked event exactly as found, reporting `skipped_ambiguous_pre_upgrade_provenance:<event ID>`. This is a deliberate, permanent accepted limitation of the pre-upgrade data itself, not a completeness gap to eventually close automatically: full automatic resolution would require guessing at exactly the question this sentinel exists to flag as unanswerable, so it is left for an operator to review by hand — see "Known limitations" below.

To backfill `Task Origin=` provenance (see "Behavior" above) onto an **existing live deployment**, call `backfillTaskOriginProvenance_()` once from the editor immediately after deploying, and **before** `backfillStoryExclusion_()` above — order matters here; the two are otherwise part of the same upgrade step. It queries **every** page regardless of Type (no Type filter at all), and for each of its Time Events that has no `Task Origin=` marker yet (i.e. predates this revision), stamps the `ambiguous-pre-upgrade` sentinel directly into the event's own Note. `reconcileStoryTask_` treats this marker as neither preserved nor archived, for every caller without exception: an already-closed event is left exactly as found, reporting `skipped_ambiguous_pre_upgrade_provenance:<event ID>` in its Outcome so an operator can review the flagged events by hand and decide; a still-**open** one is closed in place instead (bounding its duration, not resolving its origin — see "Behavior" above and round 23), reporting `closed_ambiguous_pre_upgrade_provenance:<event ID>`.

Once a call fully drains (its returned summary shows `truncated: false` and `timedOut: false`), it persists `TASK_ORIGIN_BACKFILL_COMPLETE = 'true'` in Script Properties, permanently (never cleared once set). `reconcileStoryTask_`'s ordinary archive path (see "Behavior" above) gates on this — Codex-reported gap (round 19): on an existing live deployment, the already-installed `pollTaskChanges` trigger does not wait for an operator to run this backfill, and the backfill itself can take multiple wall-clock-bounded calls to fully drain a large workspace. A Story reached by an ordinary poll during that window has an event that genuinely has no marker *yet* (not because its origin is confirmed), and archiving it would race ahead of this backfill's own ambiguous-flagging with the same real consequence: permanently erasing genuine Task-era history. Until this flag is set, `reconcileStoryTask_` treats a marker-less event exactly like an ambiguous one (`skipped_pending_provenance_backfill:<event ID>`, not archived) — so running this backfill to a full drain before relying on `backfillStoryExclusion_()`'s archive behavior is not just about flagging ambiguous data correctly, it is also what unblocks archiving genuinely bogus Story stray data at all on an existing deployment.

Deliberately does **not** attempt to infer a confirmed Task/Story origin from a page's current Type at backfill time, in **either** direction — Codex-reported gap across two rounds of this fix. An earlier version trusted a currently-non-`Story` page's Type as confirmation that its events were genuine Task-era work; a page already `Story` at backfill time was excluded from the query entirely. Both were wrong for the identical underlying reason: a page can have flipped `Type` any number of times before this revision was ever deployed, with no historical record of when. A page reclassified `Story → Task` before this deploy looks exactly like an ordinary Task page at backfill time, yet may still carry a genuinely bogus pre-fix Story stray event created while it really was a Story — the earlier version would have wrongly certified it as Task-origin, letting `reconcileStoryTask_` preserve it forever the instant it was ever reclassified to `Story` again. The mirror-image case (`Task → Story` before deploy) has the identical problem excluding Story pages from the query. No pre-existing event's origin can be confirmed from data this script has access to, so every one gets the ambiguous sentinel unconditionally — only events **created after this deploy** (via `createNotionTimeEvent_`, which stamps the real, current Type directly and immutably) ever get a confirmed `Task Origin=` value.

Resumable and pagination-bounded the same way `backfillStoryExclusion_` is (`TASK_ORIGIN_BACKFILL_RESUME_CURSOR`/`_TIE_IDS`) — call it again if its summary shows `truncated: true` or `timedOut: true`. An event that already has `Task Origin=` (created after this revision, or already backfilled) is left completely untouched, never re-stamped, so a full re-run is always a free re-scan. Retry-safe by construction: stamping an event is a single write (its own Note holds the value directly, with nothing else to keep in sync), so an interrupted or failed patch simply leaves that event unmarked for the next call to pick up again — there is no second, separate record that could desynchronize from it. Its tied-cohort resume state is tracked by **page ID** (`TASK_ORIGIN_BACKFILL_RESUME_TIE_IDS`, comma-joined), not by the raw count every other resumable pass in this file uses (`LAST_SYNC_CURSOR_TIE_OFFSET` and friends) — Codex-reported gap (round 28): a count cannot tell "an already-processed page left the tied cohort" apart from "a never-processed page left it too", so if a page this backfill already handled is edited before the next call (its own `last_edited_time` moving later, out of the tie), the resumed `on_or_after` query returns a smaller tied cohort and skipping the old, now-too-large count from it silently drops whichever page was never actually visited. Unlike a miss in any of this file's other resumable passes — recoverable next time anything touches the skipped page — a miss here is not: the page's marker-less event stays that way past `TASK_ORIGIN_BACKFILL_COMPLETE`, and `reconcileStoryTask_`'s archive path can then permanently delete it as pre-fix Story stray data even when it is genuine pre-upgrade Task-era history. That asymmetric, irreversible consequence is why only this one function pays for ID-based tracking instead of getting the same documentation-only treatment as the others' identical-in-shape (but recoverable) limitation — see "Known limitations" for where that limitation still applies to it, at genuine extreme scale.

**Run this once even on a genuinely fresh deployment, not only an existing one being upgraded** — Codex-reported gap (round 25): every event *this script itself* ever creates gets a confirmed `Task Origin=` at creation from day one, so a fresh deployment has no pre-existing marker-less event of its own. But `backfillStoryExclusion_()`'s archive path also supports a Time Event added directly in Notion at any later point (not through this script — see its own entry above), and that path is gated on `TASK_ORIGIN_BACKFILL_COMPLETE`, which stays permanently `false` if this backfill is skipped as "not needed" on a fresh deploy — silently blocking that archive path forever for any future stray data, with no automatic way to notice. A zero-result full drain still sets the completion flag (see its own "fully drained" branch), so running this once against an empty history is what unlocks that archive path going forward — cheap, since there is nothing yet to scan or flag.

## E2E

Use non-production test Tasks. Allow up to one poll interval for each step, or call `reconcileTaskById(pageId)` from the editor to reconcile immediately.

### Status start/stop

1. `Ready → In Progress`.
2. Confirm an authoritative Notion `Task Time Events` row is created with Task, Actor, and `Started At`.
3. Confirm the same Notion Event ID appears in the Sheet projection.
4. `In Progress → Review`.
5. Confirm the Notion Time Event receives `Ended At`, then the Sheet row reflects the same end time.

### Done gate

1. While a Task still has an open Time Event, set it to `Done`.
2. Confirm the integration restores `In Progress` and leaves the Time Event open; Done is not allowed to persist.
3. Move `In Progress → Review` and confirm the Time Event closes.
4. Set Done without a prior Time Event, `Result`, or `Completed At`; confirm the Task is restored to `Review`.
5. Provide required evidence and then move to Done; confirm Done persists with an existing closed Time Event.
6. **Reopen correlation**: complete a Task through Done once (closed Time Event, `Result`, `Completed At` all present). Reopen it (`Done → Backlog` or `Ready`), then move it back to `In Progress` and immediately to `Done` again within a single poll interval, so no new Time Event opens for this second execution. Confirm Done is rejected and the Task is restored to `Review`/`In Progress` — the old, pre-reopen closed event must not satisfy the gate for the new execution. Then run the normal start/stop flow for the new execution and confirm Done then persists.
7. **Stale Completed At on reopen**: after step 6's reopen, leave the Task's old `Completed At` in place (do not clear it) and run the new execution's own start/stop flow so it gets its own closed, applicable Time Event and fresh `Result`. Attempt Done without updating `Completed At`. Confirm Done is rejected (the stale, pre-reopen `Completed At` does not satisfy the gate). Update `Completed At` to a time at or after the new event's `Ended At` and confirm Done then persists.

## Known limitations

**A pre-existing event flagged `Task Origin=ambiguous-pre-upgrade` by `backfillTaskOriginProvenance_` is never automatically resolved, by any caller, including `backfillStoryExclusion_()`.** Its true origin (genuine pre-upgrade Task-era work vs. always-bogus Story stray data) is unrecoverable from any data this script has access to — a page's current Type never proves anything about its pre-revision event history, in either direction, no matter how the caller scopes its own query (see `backfillTaskOriginProvenance_`'s own entry above). Resolving it automatically in either direction risks a real failure mode: archiving erases genuine historical work, preserving indefinitely lets the double-counting bug persist. This was attempted once for `backfillStoryExclusion_()` specifically (round 17, archiving on the reasoning that the backfill only visits current Story pages) and reverted (round 18) once Codex pointed out that reasoning was the same current-Type fallacy already root-caused elsewhere in this file. Every flagged event stays `skipped_ambiguous_pre_upgrade_provenance:...` permanently, for an operator to review by hand — not a gap with an available automatic fix. **A direct consequence, worth stating plainly: on any existing deployment that follows the documented upgrade order, `backfillStoryExclusion_()`'s `archived_story_event:` outcome is not reproducible against genuinely pre-existing legacy data** (Codex-reported gap, round 20) — every marker-less event `backfillTaskOriginProvenance_()` ever finds gets flagged ambiguous in that same pass, and `TASK_ORIGIN_BACKFILL_COMPLETE` (see "Behavior" above) is never true before that has happened. The archive path remains reachable only for a Time Event this script itself never had a chance to mark, e.g. one added directly in Notion after the provenance backfill has already drained once.

**An ambiguous-marked event that is still open when observed gets closed in place, even while its page stays `Type = Story`** — fixed in round 23, closing a gap flagged (but not yet fixed) as of round 20: leaving it running indefinitely would have kept contributing to whatever downstream aggregation computes an open event's running duration (e.g. the Sheet's own `Duration (h)` formula) for as long as it stayed open, for a page that predates this deploy and never gets reclassified potentially indefinitely — reintroducing the exact double-counting this file exists to stop, for the one population (ambiguous) it wasn't yet taught to bound. `reconcileStoryTask_` now closes such an event (`Reason=ambiguous_provenance_bounded`, outcome `closed_ambiguous_pre_upgrade_provenance:<event ID>`) without archiving it and without touching its own `Task Origin=ambiguous-pre-upgrade` marker — bounding its duration, not resolving anything about its true origin; it remains fully intact and visible for an operator to review by hand. An already-closed ambiguous event is untouched either way, exactly as before. The close boundary is clamped to never precede the event's own `Started At` — Codex-reported gap (round 24): the boundary passed in is the *Story page's* own observed edit time, not this event's, and a Time Event added directly in Notion (attached via its own `Task` relation) never touches the Story page itself, so it can have a `Started At` after the page's last real edit; closing at the page's (older) edit time in that case would set `Ended At` before `Started At`, a negative duration in both Notion and the Sheet projection. The clamp only ever moves the boundary *later* (to the event's own start, at minimum a zero-length interval), never earlier.

**A Story observation can be lost if the Sync Log append that records it fails after everything else in that same `reconcileTaskPage_` call already succeeded** — Codex-reported gap (round 26). `logSnapshot_` runs last, after the reconciliation outcome (e.g. `reconcileStoryTask_` archiving stray events) and the Sheet projection sync are both already committed; if that final `appendRow` specifically throws (a transient Sheets API error), the whole poll run aborts and `LAST_SYNC_CURSOR` is left exactly where it stood before the run, so the same Task is retried in full on the next run — including its Story reconciliation and this same log append. The evidence gap is real only in the narrower window between that failed run and the next *successful* one: if the page's `Type` is changed away from `Story` to an executable Task/Subtask in that window, the next run reprocesses it through `reconcileAuthoritativeTimeEvents_` instead of `reconcileStoryTask_`, and `storyConversionHappenedWhileInProgress_` (see "Behavior" above) finds no Story-marked row for this Task ID at all — because the one row that would have recorded it never made it into the Sync Log — and can wrongly trust the page's still-Story-era `Started At` as fresh. This was deliberately not fixed by adding a second, independent evidence channel (e.g. a Script Properties marker written before the failure-prone append): this codebase has no retry or dual-write mechanism anywhere else, relying everywhere else on the same "an uncaught exception aborts the run and the unmoved cursor causes a full retry next time" behavior already described in the "resumes correctly when a stop lands inside a tied timestamp" note below — and a per-Task Properties-based cache would itself need its own staleness/cleanup handling at scale (Script Properties has a total-size budget, and nothing would ever prune an entry once written) — the same kind of added complexity repeatedly rejected elsewhere in this file in favor of the simpler, already-consistent behavior. The window requires two independent, low-probability events to coincide (a transient Sheets failure specifically on this append, followed by a manual Type change before the very next poll succeeds) and self-heals on any run that completes normally — every run in between still correctly identifies the page as `Story` and skips opening anything on it, so nothing is *mis*-recorded until the conversion actually happens. `backfillStoryExclusion_()` cannot retroactively fix an instance of this once it has happened, since it only ever queries pages whose Type currently reads `Story` — by the time this gap is reachable the page has already been reclassified away from `Story`, so an affected Task's wrongly-early `Started At`/opened Time Event needs a human to notice and correct it directly (there is no automated re-check for it, the same as the ambiguous-provenance case above).

**`backfillStoryExclusion_`'s resume mechanism cannot fully resolve a single tied `last_edited_time` group wide enough to itself exceed `QUERY_PAGE_SAFETY_LIMIT`** (thousands of Stories sharing one exact minute, e.g. after a bulk edit) — the same accepted, extreme-scale limitation `LAST_SYNC_CURSOR_TIE_OFFSET` (`pollTaskChanges`) and `BACKFILL_RESUME_TIE_OFFSET` (`backfillResultFingerprints_`) already carry, for the identical structural reason: Notion's public API offers no secondary sort key to page within an exact-timestamp tie, so once the persisted tie offset reaches the safety limit's own page size, every further call's `on_or_after` query returns only that same saturated tie and skips all of it. Not expected at real Cloud42 task volumes. `backfillTaskOriginProvenance_`'s own tied-cohort tracking (`TASK_ORIGIN_BACKFILL_RESUME_TIE_IDS`, page IDs rather than a count — see its own entry above for why) hits the identical wall from a different direction: a single Script Property has its own value-size cap, so a tie with enough page IDs to exceed it (on the order of hundreds of UUIDs) saturates the same way. Not a new gap this backfill's fix introduces — the same accepted extreme-scale ceiling every tied-cohort resume mechanism in this file already has, just reached via storage size here instead of a count.

The reconciler intentionally uses the Task's **current authoritative state** rather than a change history. A Task edited into and back out of `In Progress` inside a single poll interval is only ever observed in its final state, so that intermediate spell is not recorded. This is the same property the webhook design had — Notion aggregates `page.properties_updated` deliveries — and the PoC must evaluate whether those transitions matter at real Cloud42 task timescales.

**A legacy (pre-`Execution=`) event that is genuinely a Task's only execution can be wrongly excluded once retroactively Boundary-marked, with no available fix at this call site.** When a Task leaves `In Progress` with nothing open to close (its only actor already reassigned away earlier), `reconcileAuthoritativeTimeEvents_` retroactively stamps `Boundary=left_in_progress` on the most-recently-closed event so `enforceDoneGate_`'s legacy Reason/Boundary heuristic can tell that execution actually ended there. An earlier version also backfilled `Execution=` at the same time, from the Task's own *current* `Started At`, specifically to save this one case: a legacy event that is that Task's only (and therefore current) execution would otherwise fall back to the heuristic and be wrongly treated as prior evidence against itself, permanently blocking Done. That backfill was removed after it was shown to be unsafe: this call site cannot distinguish that case from a Task reopened and restarted entirely inside one poll window (the paragraph above) — there, the Task's current `Started At` already reflects a new, never-observed execution while the closed event is still evidence from the old one, and the same backfill would tag that stale event as belonging to the new execution, letting a Done with no valid Time Event for the new execution pass anyway. Both cases reach the same branch with identical information available, so there is no way to tell them apart there. The fix keeps only the `Boundary=` stamp and never backfills `Execution=`, closing the second (silent wrong-accept) failure at the cost of reopening the first (a legitimate, unique Done blocked until a Human or governance intervenes to re-record `Started At`/`Result` for that Task) — the narrower and safer of the two to leave open. Closing it outright would require the reconciler to have positively observed the Task's actual restart (an open event for the new execution), which is exactly what the invisible-reopen case above means it may never see.

The Done gate is reactive: it observes a Status that has already been set. An invalid Done may exist for up to one poll interval before the reconciler rolls it back, but it cannot remain Done once the Task is reconciled. Durable completion still requires the Time Event and completion evidence first.

`last_edited_time` is minute-granular, so two distinct edits to the same Task within one minute produce the same reconciliation snapshot and are reconciled once, against the later state.

**Recorded boundary timestamps carry a backlog-dependent imprecision, for a structural reason.** `Ended At` (and a reassignment's actor-boundary timestamp) is set from `task.last_edited_time` at the moment the reconciler observes the Task leaving `In Progress` — but that field is the *page's* last edit time, not a per-property change time, because Notion's public API does not expose one. If an unrelated property (e.g. `Result`) is edited after the actual status transition but before any poll observes the page in between, `last_edited_time` reflects that later, unrelated edit, and the recorded `Ended At` is inflated by the gap. This is only possible when **no poll ever observed the Task at its true transition instant** — which requires either (a) both edits landing within the same poll interval, or (b) the transition's own reconciliation being deferred by a run that hit `MAX_TASKS_PER_RUN` (25 write-producing Tasks per run) before reaching it. `pollTaskChanges` never defers indefinitely — every run either reconciles a Task or holds the cursor at the exact point it stopped, and a zero-Notion-call re-read (`duplicate:`/`ignored:`) never counts against either cap, so a cohort sharing one timestamp cannot itself cause an unbounded stall (see the fix for "Continue scanning beyond a duplicate timestamp cohort" — a large *write-producing* backlog is a distinct case, covered next). But case (b)'s delay is **not** capped at one extra poll cycle: if more than 25 write-producing Tasks sort ahead of the target inside the same incremental window, the target can be deferred by up to `ceil(backlog / 25)` poll cycles, and if a further unrelated edit lands on the target during that backlog, the inflation spans that many intervals, not just one. There is no page-history or property-level-timestamp endpoint in Notion's public API to close the underlying gap outright; narrowing `POLL_INTERVAL_MINUTES` narrows same-interval exposure (case (a)), and keeping `MAX_TASKS_PER_RUN` write-backlogs short in practice bounds case (b). This is a known, bounded-but-backlog-dependent limitation of polling `last_edited_time`, not a bug with an available fix — do not treat recorded boundary timestamps as accurate to the second, or even reliably to one poll interval under a sustained large backlog.

**A single abnormally slow Notion request can still exhaust `backfillResultFingerprints_`'s reserve, since Apps Script exposes no per-request timeout to bound it.** `paginateNotionQuery_`'s deadline check runs once per loop iteration, before that iteration's request is issued — it bounds when a new request may *start*, not how long the run's wall clock has actually advanced once that request *returns*. `MIN_PROCESSING_RESERVE_MS` is sized (65 seconds) to cover the worst-case duration of one single `UrlFetchApp.fetch` call, so that a request permitted to start still cannot, by itself, push elapsed time past the run's own outer `MAX_RUN_DURATION_MS` bound. This guarantee holds only under the assumption that no single Notion request takes longer than the reserve — Apps Script does not document or expose a configurable fetch timeout, so this is an inference from commonly observed platform behavior, not a guaranteed SLA from either Google or Notion. A request slower than that assumption can still, in the worst case, leave the processing loop with zero usable time for that one call — safely (no data is lost or corrupted; the checkpoint is simply left untouched, and the next call retries), but not productively. This is a known, bounded-but-not-provably-eliminated limitation of a synchronous HTTP call with no client-side timeout control, not a bug with an available fix within this PoC's scope.

**`Note`'s Result-fingerprint history is bounded, not unbounded, for a structural reason.** `enforceDoneGate_`'s stale-Result check needs *every* fingerprint an event has ever been stamped with, not just the latest (`noteFieldAll_`), since a reopen can restore an old, already-seen `Result` value rather than a genuinely new one. `Note` is a single Notion rich-text field with a practical size ceiling, so `appendNote_` caps combined length at 1800 characters and, when a new marker would exceed it, evicts the oldest segment first — but only a non-fingerprint one (`Reason=`, `Snapshot=`, `Changed By=`, `End Status=`; only the newest of each ever matters, so losing older copies is harmless). Only once *none* of those remain does it fall back to dropping the oldest `Result Fingerprint=` segment, the last thing it will ever evict. At roughly 65 characters per stamped fingerprint (`Result Fingerprint=` plus a 43-character SHA-256 digest), that leaves room for on the order of 25–27 executions' worth of stamps on one event before the oldest is ever evicted — an event would need to be reopened and re-stamped with a distinct `Result` value that many times before eviction can even begin. Once it does, the oldest fingerprint's protection is genuinely lost: a Result value that happens to match one of the evicted (rather than still-retained) old values would no longer be caught as stale. Closing this outright would require either splitting fingerprint history across multiple Notion rich-text segments/properties or a dedicated schema change, both beyond this PoC's scope; this is a known, bounded-but-not-eliminated limitation of storing unbounded history in one bounded field, not a bug with an available fix at this size.

## Success criteria

- Notion remains authoritative for Task state and Task Time Events.
- Sheet rows are reproducible projections of Notion events for touched Tasks.
- No credential appears in any URL, and no public endpoint exists to hold one.
- `NOTION_TOKEN` is the only secret, held only in Apps Script Script Properties, and never logged.
- The reconciler is reachable only from inside the Apps Script project (time-driven trigger, or an operator running `reconcileTaskById` from the editor).
- Beyond the Notion API responses it fetches itself, the reconciler accepts no externally supplied operational claims.
- Human / Chris / Claude / Codex Task activity uses the same state-driven mechanism.
- In-progress reassignment/clearing cannot leave the original Actor event open indefinitely.
- Done cannot persist without a closed Time Event **applicable to the current execution** (started at or after the Task's current `Started At`, itself required to look fresh relative to the Task's own event history), a `Completed At` that is itself no earlier than that Started At or the applicable event's own Ended At, and a `Result` that was actually validated for this execution (not merely present). A closed event, `Started At`, `Completed At`, or `Result` left over from a prior, already-completed execution does not satisfy a later reopen's Done gate.
- An invalid Done cannot escape re-verification through a minute-granularity snapshot-hash collision; Done is always re-checked.
- Repeated reconciliation of an unchanged Task does not duplicate authoritative events.
- A Task already `In Progress` before the first-ever poll still receives an open Time Event, via the fresh-deploy bootstrap.
- A dense cluster of already-reconciled Tasks inside the overlap window cannot permanently stall reconciliation of Tasks behind it.
- A `Type = Story` page never opens a Time Event and is never subject to the Done gate; every Time Event it accumulated before this exclusion existed — open or already closed — is archived (not merely closed, which would still count a fictitious duration) rather than left in the authoritative data.
- A reopened Task's new interval starts from its current `Started At`, not from a later edit the poll happens to observe first.
- A current execution that produced more than one closed event (e.g. an in-progress reassignment, including one that leaves a real time gap such as an assignment being cleared and only later reassigned) is not mistaken for stale prior-execution evidence — and a genuinely prior execution's closing event isn't mistaken for current-execution evidence just because it happens to coincide in time with something in the new one.
- A large free-outcome scan (duplicates, or a large already-Done cohort) cannot run long enough to risk an uncaught Apps Script execution-limit kill; it stops and persists a resumable cursor first.
- A capped run that stops inside a group of Tasks sharing one identical `last_edited_time` resumes past exactly what it already reconciled on the next run, rather than rescanning the same tied prefix forever.
- Normal conversation and non-Task activity create no event.
